# CC parity adapter (OpenCode V1)

An OpenCode (OC) V1 plugin, in the `personal` plugin, that reads Claude Code's (CC) own
configuration and re-creates as much of it as OC can honour. It targets OC 1.19.0 only, and an OC
version change is reported once in the parity line. Nothing is copied or generated by hand: the
adapter derives everything at OC start from CC's files, so CC stays the single source of truth.

The rule throughout: OC may be stricter than CC, never looser. Where a translation is lossy, an
error occurs or a CC record is missing, the adapter fails closed.

## What it derives

- **Settings:** the stack `~/.claude/settings.json`, then `<project>/.claude/settings.json`, then
  `<project>/.claude/settings.local.json` (scalars: highest wins; permission lists: merged).
  **CC's trust gate applies:** the two project files load in full only when `~/.claude.json` has
  `projects[<dir>].hasTrustDialogAccepted === true` for the git worktree's main repository, or for
  the directory or a parent, the walk stopping at the nearest `.git`, as CC's own check does.
  Otherwise only their `permissions.deny` loads, and the directory is reported once ("project
  settings not trusted in CC; hooks and allows skipped"). An untrusted project's `.mcp.json`
  servers never start.
- **Permissions:** CC `allow`/`ask`/`deny` rules merged into OC's `permission` on top of the
  OC-owned baseline in `opencode.json` (the adapter never replaces it). A deny or ask with no exact
  OC form is emitted as an over-matching superset at the same action (see Known gaps); an allow with
  no exact form is dropped and reported. Calls neither CC nor the baseline covers get CC 2.1.300's
  own default for the tool (table in `docs/v1-capabilities.md`): `bash` and `edit` get `"*":"ask"`
  first, `webfetch` and `websearch` get `"ask"`, each skill whose `SKILL.md` sets `allowed-tools`,
  `disallowed-tools` or `hooks` gets `"<name>":"ask"`, and every configured MCP server gets
  `"<server>_*":"ask"` ahead of CC's allows for it. `task` and `todowrite` get nothing: CC runs
  subagents and TodoWrite without a prompt. The adapter never adds a top-level `"*"` (one in the
  baseline is kept as is): it would loosen OC's built-in
  `question`/`plan_enter`/`plan_exit` denies. OC's built-in agent denies are re-asserted per agent,
  merged after the user rules as OC does, so no key the adapter adds loosens them: the edit deny of
  plan, explore, compaction, title and summary (plan keeps its plan-file allow unless a CC
  Edit deny covers that file); for the deny-all built-ins (explore, compaction,
  title, summary) `task`, `skill`, every `<server>_*`, and `webfetch`/`websearch` except where the built-in
  allows them (explore); plan's `task` deny for `general`; and general's `todowrite` deny. Built-in
  allows are never touched, and your own agent-level rule for a key still wins.
- **Hooks:** CC command hooks, run through OC's tool and chat hooks with CC's JSON protocol
  (exit 2 blocks, structured JSON output, `continue:false`, matchers, `if`, timeouts in seconds).
  Other handler types (`prompt`, `http`, `agent`) are reported as unknown and never run.
  On Windows a shell-form hook whose first word ends in `.sh` runs as `bash <command>`, as CC does,
  so a `~/...sh` hook works under a home path with a space. A hook whose first stdout line is
  `{"async":true}` is detached after that line, as in CC.
- **MCP servers**, mirrored with their scope and exposed as `<server>_<tool>` (translated to and
  from CC's `mcp__<server>__<tool>` so matchers work).
- **Skills and agents** from CC's user, project and enabled-plugin directories.
- **Enabled plugins**, resolved only through `installed_plugins.json` (user-scope record, then its
  install path, filtered by merged `enabledPlugins`).

Anything that cannot be translated faithfully is reported as unknown rather than guessed. For
permission denies and asks, "reported" never means "dropped": they are still enforced, over-matching
if need be.

## Dispositions

Every hook gets a disposition from `core/dispositions.json`:

| Disposition | Meaning |
|---|---|
| `bridge` | Runs with CC semantics. Unclassified hooks bridge, and are reported once. |
| `degraded:<reason>` | Runs, but not with CC semantics. Reported once. |
| `skip:<reason>` | Deliberately not run (an OC equivalent exists, or it is cosmetic). Never reported. |
| `cc-only:<reason>` | Needs something OC never supplies. Never reported. |

## The parity line

The first message of a top-level session carries one compact line, for example
`CC parity: 2 unknown (...) | 1 degraded hook (...) | full list: <path>`. Items are grouped by kind
with counts and up to three short names per group, and the line shrinks until it fits. Kinds, in
order: not-translated settings, unknowns (settings, permissions, MCP, agents, commands, untrusted
project directories), unclassified bridged hooks, degraded hooks, hook failures, problems,
release-note drift (kind 3), OC version changes, self-probe mismatches. Each item is reported once
(it is marked seen only after it was inserted); failures are drained by the delivery that reports them.

The full text of every item, plus runtime errors and hook failures, goes to
`<OC data dir>/cc-parity.log`. State lives in `<OC data dir>/cc-parity-state.json`.

## Tests

```sh
cd personal/opencode
bun test                                              # safe bare: bunfig.toml preloads test/setup.js
bash test/make-scratch-home.sh                        # scratch HOME for manual runs
```

`test/setup.js` (a `bunfig.toml` `[test] preload`) points `XDG_DATA_HOME`, `CC_PARITY_STATE` and
`CC_PARITY_DISPOSITIONS` at a fresh temp dir unless you already set them, and removes that dir after
the run, so a bare `bun test` never touches the real state file or `cc-parity.log` and never reads your
own `cc-parity-dispositions.json` (the dispositions path is left nonexistent). Fixtures use temp dirs; nothing depends on the machine running them.
`make-scratch-home.sh` copies the real `auth.json` (credentials) into the scratch dir: delete that
dir after use (`make-scratch-home.sh --teardown <dir>`).

Hook classification: `core/dispositions.json` ships only plugin-keyed and already-public rules. Your own
hooks go in `<OC config dir>/cc-parity-dispositions.json` (same schema, `CC_PARITY_DISPOSITIONS`
overrides the path); it is merged over the shipped rules and your entries win. A missing file is fine;
a malformed one is logged, reported as an unknown item, and ignored.

## V2 move criteria

This adapter stays on OC V1 and is split into a Claude-Code-reading core plus a thin V1 front-end,
so a move to V2 is cheap. V2 gaps today: it reads no `CLAUDE.md` (only `AGENTS.md`) and ignores
`instructions` entries; plugins cannot add agents (`AgentEditor` has no `add`); a plain-JS
before-hook `throw` becomes a defect rather than a `Tool.Error`; it does not run LSP;
context-hook injection may not reach the model (gh #44788); 2.0.28 shipped with a reproduced
plugin-load regression (gh #55154); and V1 has no announced end of life.

Re-check these when deciding. Any one of 1-3 makes a move worth re-evaluating, and 4 forces it:

1. gh **#44788** is closed, **or** a canary string injected through `session.hook("context")`
   comes back from the model on the current 2.0.x.
2. gh **#55154** is closed **and** a plugin loads on Windows on a clean service.
3. V2 restores the `AGENTS.md`/`CLAUDE.md` fallback or `instructions` loading, **or**
   `AgentEditor.add` exists.
4. V1 gets an announced end-of-support date.

## Known gaps

- **Plugin language servers are not translated.** `lspServers` (in `plugin.json` or inline in the marketplace entry, as `gopls-lsp` and `typescript-lsp` do) is reported once (like every parity item); OC has its own LSP configuration. Inline `mcpServers` in a marketplace entry (as `qmd` does) *is* enumerated, when the plugin has no `plugin.json`, as CC does.
- **A command's `allowed-tools` is not carried.** In CC it pre-approves those tools while the
  command runs; OC has no per-command grant, so they prompt per the session's permissions instead.
  Stricter only, so it is documented here rather than reported in the parity line.
- **Command arguments get CC's rules on OC 1.19.x only.** OC numbers `$N` from 1, blanks an
  index with no argument and gives the highest index the rest of the arguments; CC numbers from 0
  and leaves an unfilled index literal, so a body such as commit-commands' `awk '{print $1}'` only
  survives under CC's rules. The template OC receives is still remapped; then the
  `command.execute.before` hook replaces OC's rendered text, in place, with the CC body rendered by
  CC 2.1.302's rules (`$N`, `$ARGUMENTS[N]`, `$ARGUMENTS`, `\$` escapes, the `ARGUMENTS:` line CC
  appends when nothing was filled, `!` defused in values). Limits: a body with an OC shell block
  (`` !`cmd` ``) and `$N` keeps OC's rendering, because OC runs the block before the hook, and is
  reported; on any OC outside 1.19.x, or when the version is unknown, the hook changes nothing
  (it relies on OC firing it after rendering and reusing its own parts array), and the parity line
  says so once per version; arguments are split like a shell for plain words and quotes, but shell
  syntax in an argument (operators, `$VAR`, `VAR=x`) may split differently from CC's bash parse;
  named arguments (`arguments:` frontmatter) are not substituted (reported as before); and the
  `@file` attachments OC resolved from its own rendering are kept as they are.
- **No PowerShell tool** on the OC side, so CC hooks and rules that target it have no counterpart.
- **OC auto mode has no classifier.** CC's auto-mode behaviour is not reproduced.
- **A hook `ask` blocks.** OC cannot prompt from a hook, so an `ask` decision denies.
- **A hook's `continue:false` blocks; it does not stop the turn.** On `PreToolUse` and
  `UserPromptSubmit` it blocks with its `stopReason` (default "stopped by hook"), ahead of any
  decision field, as in CC; OC cannot end a turn from a hook, so the model may carry on. On other
  events it is logged as not honoured.
- **Untranslatable denies and asks over-match.** `/path` (relative to a settings file the merged
  rules no longer name) becomes `**/path`; a character class `[ab]` becomes OC's `?`; an MCP server
  glob `mcp__srv*` becomes one key per configured server it matches plus `srv*_*`, except
  that a glob key which would also match an OC built-in permission (`mcp__*` gives `*_*`, which matches
  `external_directory`, `plan_enter`, `doom_loop`, ...) is left out and reported, so a server added later
  is not covered; `Grep(x)`, `Glob(x)`, `LSP(x)`, `WebSearch(x)` and
  `TodoWrite(x)` set the whole key; a `!` negation, which has no superset, asks on the whole key.
  These can block or prompt for calls CC would allow, and each is reported.
- **More prompts than plain OC.** Uncovered `edit`, `webfetch`, `websearch`, MCP calls and skills that
  declare tools or hooks ask (bash already did), as in CC, where OC's default would allow them.
  WebFetch asks even for the hosts CC preapproves. A guarded skill (one that declares tools or
  hooks) still asks under a CC whole-tool `allow:["Skill"]`, where CC would run it; a `Skill(name)`
  allow does lift it. CC's held-back plugin-skill cases and its coordinator-mode skill allow are
  not reproduced either; both only make OC stricter.
- **OC built-in collisions.** OC matches a top-level key against every permission name, so an MCP
  key that also matches `plan_enter`, `plan_exit` or `question` (a server named `plan`, say, or one a
  glob expands to) is emitted as deny rather than ask, and such allows are dropped. A configured
  server named `plan` therefore gets `plan_*: deny`, which also denies the plan agent's
  `plan_exit`. `AskUserQuestion` and `ExitPlanMode`
  are gated by visibility in OC: a CC deny on them is a deny, while an ask or allow emits no rule
  and is reported (OC's plan exit and question tools put the call to the user themselves).
- **Plan's plan-file edit allow yields only to a covering deny.** It is dropped when a CC Edit deny
  matches its whole key (`.opencode/plans/*.md`); a narrower deny such as
  `Edit(.opencode/plans/secret.md)` leaves it in place, so the plan agent can still edit that file.
- **Trust follows the repository.** A nested repo with its own `.git` is not covered by a trusted
  parent; a git worktree is covered by its main repository's entry, as in CC.
- **Failures fail closed.** If the CC inventory fails, no CC hooks run and the baseline gets an
  ask for `bash`, `edit`, `webfetch`, `websearch`, `skill` and every MCP server; the same overlay
  applies if the config hook fails before the CC permission is in place. An internal adapter error
  blocks a tool call whenever a CC `PreToolUse` hook may apply to it.
- **A hook's `updatedInput` that OC cannot apply blocks the call.** That covers an OC call mapped
  to several CC calls (`apply_patch`), a tool with no reverse arg map (MCP and the rest), and a
  rewritten field the OC tool has no arg for. The original input never runs in place of a rewrite.
  As in CC, `updatedInput` REPLACES the input: a key the hook leaves out is dropped. On `bash` and
  `edit` a dropped optional arg (`timeout`, `replace_all`) is removed from the OC args; dropping a
  required one, or any key on a tool with no reverse map, blocks. An `updatedInput` that echoes the
  call's input back exactly rewrites nothing and passes on every tool.
- **A CC `Task`/`Agent` rule suppresses OC's child-session `task` deny.** OC adds that deny only
  when the subagent has no `task` rule, and a user-level `task` key gives every agent one. It is
  reachable only with `subagent_depth` above 1; at the default 1, OC refuses a nested task before
  asking.
- **An untrusted project's skills, agents and commands still load.** They are content, not
  permissions, and OC loads its own project content without a trust gate too.
- **`prompt`- and `agent`-type `PreToolUse` guards are not enforced.** Only `command` hooks run;
  the others are reported as unknown.
- **superpowers' `V1_MAPPING` points every model at `apply_patch`**, which only GPT models have.
- **OC grep/glob ignore read denies.** CC `Read` denies do not protect file contents from OC's
  search tools. This is OC behaviour, reported in the parity line.
- **WebFetch domain rules become a global ask**, and remembered domain allows are lost.
- **Code Mode `execute` permission:** any restricted agent with at least one `mcp__` tool gets an added `execute` permission so their
  MCP tools keep working under Code Mode.
- **Restricted CC agents are enforced through a per-agent `permission`**, because OC ignores a
  `tools` set from a hook.
- **Pass-through tool argument shapes are unmeasured.** Tools the tool map passes through without
  a measured arg shape may not translate exactly; the self-probe only checks the names it knows.
- **Kind-3 detection fell back to a digest.** See the measurement below: the gate failed, so the
  detector emits one compact item per CC-version change rather than a list.
- **First-message caveat:** the parity line goes into the first qualifying message of a
  top-level session. `chat.message` cannot tell a user's prompt from another plugin's `noReply`
  prompt (see "Where the parity line lands").
- **Windows: a `~/` hook command that is a single word with no `.sh` (`~/bin/x`, no arguments)
  fails under a home with a space.** A command with no whitespace goes to Git Bash unquoted, Git
  Bash expands its `~` before bash starts, and bash splits the path. Any whitespace in the command
  (`~/bin/x arg`) makes it quoted, so that works. CC 2.1.300 leaves such a command alone too, so it
  fails there as well. `bash ~/bin/x` or a `.sh` name works.
- **At exit, OC waits for Stop hooks and cancels async ones, as CC does.** A synchronous Stop hook
  (OC starts it without awaiting) still running when OC disposes the plugin is awaited, up to its
  own `timeout` plus 10 s, so its failure is logged and reported next session. So `opencode run` can
  wait for a slow synchronous Stop hook. Async Stop hooks never stretch that wait and are never
  counted. A detached hook still running (`async`, `asyncRewake`, or `{"async":true}` on the first
  stdout line; Stop and SessionEnd hooks included) is not waited for: its process tree is killed and
  it is recorded as cancelled, not as a failure, as CC's own teardown does. The kill is best effort:
  when the hook's own process has already exited while a background child still holds its output,
  that child can be left running, since the exited process's id is never reused for a kill (R28).
  A synchronous Stop hook still running at an exit that skips dispose is recorded as a failure,
  "pending at exit".
- **Async hook timeouts.** A hook configured `async`/`asyncRewake` is killed at its own `timeout`
  and counted as a failure, as before (CC clears that timer as well, and kills such a hook only at
  exit). A hook that declares itself async on its first stdout line
  has its timeout cleared at that line, as in CC: it runs until it exits or OC exits. `asyncTimeout`
  is not a kill timer here or in CC 2.1.300, which only logs it. An async hook's later JSON answer
  is not delivered: OC has no way to inject it after the call, and no rewake.
- **`GET /config` exposes expanded MCP secrets locally**, as OC's own `{env:}` substitution does.
  If you serve OC (`opencode serve`/`web`), set `OPENCODE_SERVER_PASSWORD`.

## Kind-3 detector

`core/releasenotes.js` scans Claude Code's CHANGELOG for backticked identifiers (hook events,
hook or output fields, settings keys, env vars) that the adapter does not know about. It is
gated per OC start: it only looks at the releases between the CC version recorded at the last
start and the current one.

### Pre-registration (written before measuring)

- Typical gap between OC starts: 7 days = about 6 CC releases.
- Prediction: `novelLines` fires on at most 1 of the last 10 such 6-release windows.
- Gate: at most 3 of 10 windows (about 30% of OC starts after a week's gap), else tighten the
  identifier shapes and re-measure.

### Measurement (2026-10-15, real changelog 2.1.283 to 2.1.300, ten sliding 6-release windows)

| Identifier shapes | Windows firing | Novel lines per window |
|---|---|---|
| Loose first cut (the three brief shapes) | 10 of 10 | 94,90,59,68,45,58,60,53,76,66 |
| Humps and underscore required | 10 of 10 | 54,48,27,29,18,25,24,22,38,36 |
| Final: hook-event-like, lowerCamelCase, `CLAUDE_`/`ANTHROPIC_` env | 10 of 10 | 52,45,24,26,16,23,22,21,36,35 |
| Hook events only | 10 of 10 | 7,5,2,4,3,3,2,2,3,2 |
| Settings keys only | 10 of 10 | 28,22,11,12,8,12,10,10,17,18 |
| Env vars only | 10 of 10 | 19,19,11,10,5,8,10,9,16,16 |

The prediction (at most 1 of 10) and the gate (at most 3 of 10) both FAILED. No identifier shape
passes, because CC adds new settings keys and env vars in nearly every release. Shapes alone
cannot meet the gate; the gate was not changed. Removed/Deprecated lines are skipped (0 of 300
measured lines in these windows; 4 of 641 over the whole file).

### R40 rescope (pre-registered before re-measuring)

The shape-only design above is the honest record: it measured 10 of 10 windows against a gate of
at most 3. R40 changes the detector's scope, not the gate. Settings keys and env vars only affect
parity once the user sets them, and `enumerate` reports those the first time they appear. What can
change behaviour with no config footprint is the hook protocol.

New rule: a changelog line counts only if it mentions `hook` (case-insensitive) AND carries a
novel identifier (same final shapes, same Removed/Deprecated skip).

- Prediction: fires on 5 to 7 of the same ten 6-release windows (about 6), so the gate of at most
  3 of 10 is expected to FAIL again. Hook lines with a novel identifier looked like roughly one
  per release in window 0 (`WorktreeCreate`, `PermissionRequest`, `updatedInput`,
  `updatedMCPToolOutput`, `CLAUDE_ENV_FILE`).
- Gate: unchanged, at most 3 of 10. If it fails, fall back to one compact item per CC-version
  change ("N hook-related changelog lines mention identifiers the adapter doesn't know; top 3:
  ...") and record the failure here.

### R40 result (measured 2026-10-15, same changelog copy and ten windows)

Hook-scoped rule: 10 of 10 windows fire (7,4,2,6,5,6,7,7,7,3 lines). The prediction (5 to 7) was
wrong and the gate of at most 3 of 10 FAILED again. Per the fallback, the detector delivers one
compact item per CC-version change through `hookDigest`:
"N hook-related changelog lines mention identifiers the adapter doesn't know; top 3: ...".
The gate was not changed. `novelLines` still returns the full list for the log.

### Detector details (fix round 1)

- On lines that mention a hook, a novel single-word PascalCase identifier (`Notification`,
  `Elicitation`) or snake_case identifier (`hook_event_name`, `tool_input`) also counts. The
  camelCase, PascalCase (two or more words) and `CLAUDE_`/`ANTHROPIC_` shapes are unchanged. Known
  gap: a hook mention is judged per line, so a bullet whose second (wrapped) line carries the
  identifier is missed.
- `hookDigest` returns nothing unless both versions are bare semvers and the stored one is lower than
  the current one. First run (nothing stored), a failed `claude --version`, a downgrade and no
  change all produce no item; the changelog is never scanned open-ended.
- "top 3" is deliberate: the first three distinct novel identifiers, MOST RECENT RELEASE FIRST (and
  file order within a release). It is recency, not relevance, so mod-API names can appear.
- Changelog headings: a level-2 heading yields its leading semver (`## 2.1.0`, `## [2.1.0] - date`,
  `## v2.1.0 (date)`, `## 2.1.0-beta.1` all give 2.1.0). Any other level-2 heading
  (`## Unreleased`) ends the entry and its bullets are dropped.
- Reproduce the measurement: window i = releases in (entries[i+6], entries[i]] of the newest-first
  parse, i = 0..9, on the changelog fetched 2026-10-15 (newest 2.1.300). The snapshot is not committed.

## V1 front-end (Task 10)

`adapter.js` exports `id`, `server(ctx)` and a default `{ id, server }`. The default export is what
makes the file loadable by OC v1.19.0 directly: without it OC's legacy path calls every named
export as a plugin function and throws on the string `id`.

### Drift in OC's own surface is reported one session late

`tool.definition` fires per model request, after `chat.message`, and only for built-in tools
(never MCP). `tool.execute.before` records each tool's arg names. Both are persisted into the
state file during the session and compared at the NEXT session's first message: an OC tool id with
no tool-map row becomes an unknown, and an arg name the tool map does not expect becomes a
self-probe item. So a change in OC's tool surface shows up one session after it first appears. The
self-probe runs at every start (seen-state reports each mismatch once); gating it on an OC version
change would miss renames, because the version is recorded in the same session the new names are.

### Where the parity line lands

The parity line and SessionStart context go into the first `chat.message` of a top-level session,
as one synthetic text part. `chat.message` cannot tell a user's prompt from another plugin's
`noReply` prompt: OC passes only `sessionID`, `agent`, `model`, `messageID` and `variant`, and
`opencode run` without `--agent`/`--model` sends the same shape as another plugin's nudge. So
the part goes to whichever qualifying message arrives first; a `noReply` message is still in the
history the model reads, and a concurrent message in the same session waits for the delivery.
Items are marked seen only after the push; failures are drained and the CC and OC versions recorded
only after it too.
